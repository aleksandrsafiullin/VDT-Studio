# Owned Ollama residency and contention

L04 adds a FIFO queue to the shared host-owned local HTTP transport. Each owning Node process permits one active generation and four waiting jobs by default. Metadata probes bypass inference admission. A scheduler lease spans the response body, including streaming. Cancelling a waiting request removes it before dispatch. Cancelling an active request waits for the owned transport's body cancellation before admitting the next request. A full queue returns `LOCAL_INFERENCE_QUEUE_FULL`. Pending calls revalidate their exact host model and profile at dispatch.

An immutable owned native Ollama connection can select 5, 15 or 30 minutes. The host inserts that request's `keep_alive` from its connection profile and refuses caller-supplied overrides. Changing profiles invalidates the old queued work. Existing compatibility connections and their external daemons continue to use their configured settings. This introduces no global daemon configuration or preference migration. [Ollama chat API](https://docs.ollama.com/api/chat)

The same transport contract applies to owned Model Agent and local-runner tasks. The implementation does not establish a host-wide arbiter across separate processes or between the Apple and speech services. The discretionary timer is a model residency request and remains subject to the daemon's memory and eviction policy. The host does not qualify an external loopback process merely because it accepts the option. [Ollama local runtime and memory configuration](https://docs.ollama.com/faq)

## Isolated Ollama probe

The probe starts one disposable loopback daemon at a time and uses only pinned model assets cloned onto the same SSD. It checks the manifest and each referenced file's SHA-256 and size before launch. It binds a distinct temporary port, sets cloud disabled, one runner and one loaded model in that process, and protects the existing daemon and artifact store from writes. A macOS sandbox policy limits outbound connections to loopback. The probe stops and joins its own process group. Compatibility catalog IDs can differ from the versioned manifest hash reported by the isolated server. The probe verifies the isolated catalog against the pinned manifest.

Each cohort begins with an empty resident-model list from a fresh daemon. A cold response is followed by a warm active request and a queued warm request. A third, waiting request is cancelled before dispatch. These are short, exact-answer transport probes, and engine durations overlap end-to-end measurements. Each residency value has one cold and two warm observations. Results describe visible residency deadlines after the requests, and a deadline is distinct from observing eventual eviction. The probe and redacted individual readings form development evidence. Packaged process ownership and a separately instrumented network and speech-contention test are release gates.

On the 16 GiB Apple M3, all nine sent requests gave the exact accepted answer and all three cancelled waiting jobs made zero model requests. The cloned model `qwen3.5:4b-q4_K_M` reported 3.15 GB resident entirely on GPU at 4,096 context tokens. Host swap stayed near 4,241 MiB. Prompt evaluation saw 20 tokens and generation two tokens per sent request. The results establish a warm benefit for this probe and successful residency negotiation. They give no reliable latency winner across settings. Five minutes is the shortest measured residency and was sufficient for the immediate repeat. That initial run measured advertised deadlines. A full factor-tree workload, combined speech/inference pressure, cross-process contention and signed packaged operation remain untested by this probe.

The bounded observations are in `output/apple-local-ai-voice-2026-11-25/l04/residency.json` and `residency.csv`. From the repository root, run the [measurement script](../../scripts/measure-ollama-residency.mjs) using Node 24 with `node --import tsx scripts/measure-ollama-residency.mjs`. Its arguments are a disposable cloned model store, a macOS sandbox policy file and a fresh JSON result path. Stage only the pinned manifest and its seven blobs. The sandbox allows loopback outbound and denies writes to the shared Ollama settings and installed model store. The script does not use the shared Ollama port, pull assets, unload a shared model, or alter launch settings. A controlled external-traffic observation and production verifier remain separate from this isolated development probe.

## Observing natural idle expiry

The measurement script can wait for actual model disappearance when invoked with `--observe-expiry`. Add `--model qwen3.5:4b-q4_K_M` or `--model qwen3.5:9b-q4_K_M` and repeat `--minutes 5|15|30` as needed. The default model is 4B and the default duration selection is all three profiles. Use a fresh JSON path for each cohort when running both models. Each model requires its own disposable store with the exact manifest and its seven assets. Clone files on the same APFS volume and use the loopback-only sandbox policy. The daemon uses temporary storage alongside the clone. Its sandbox permits Ollama startup to check key-file metadata and denies key contents and writes to the installed Ollama settings and model store. The probe verifies ownership of the listening process before sending requests.

After the last generation response, the probe polls resident-model metadata on the same daemon every two seconds without further inference. It records monotonic idle times for the last resident reading and the first absent reading, checks the daemon's reported deadline, and ends the wait within a bounded interval after that deadline. The report records early eviction, deadline changes, clock discontinuities, missed observation windows, interruption and cleanup status separately. A successful idle-expiry result requires continued visibility near the deadline and an absent reading before the grace window closes. A failed cohort sets a nonzero exit status and its checkpoint remains available. Pending cohorts are visible in the report.

A fully serialized run for both models waits approximately 100 minutes, plus startup, samples and shutdown. Run the 5-minute pair first, then 15 minutes and 30 minutes, keeping the host awake and running one cohort at a time. Host memory pressure, swap and GPU placement observations describe that session. They do not certify deployment hardware, longer production workloads or concurrent audio use.

On November 27 the same 16 GiB Apple M3 ran the exact 4B pin for one 5-minute expiry cohort. The daemon advertised 299.998 seconds of remaining residency. After 150 metadata polls, the model was last visible at 298.370 seconds of monotonic idle time and first absent at 300.372 seconds. The cold, warm and queued requests all returned the expected answer in 1,259.10, 111.80 and 216.87 ms. The disposable process group exited, and both cloned model stores were removed after verifying the installed manifests and all referenced blobs again. The 4B 15- and 30-minute expiries and all 9B expiries remain unmeasured. The development receipt and clone cleanup record are in `output/apple-local-ai-voice-2026-11-25/residency-expiry.1nk2j3nE/` as `4b-5.json` and `cleanup.json`.
