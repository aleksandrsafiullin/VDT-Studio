## Latest user intent and preservation boundary

The user now requires four changes: adding incoming KPIs makes their non-root parent **Calculated**; Smart proposes and applies a calculation formula together with the children; users can select part of a proposal and add their own named/unit-bearing rows in the same batch; comments in the panel become much shorter.

This explicitly supersedes the earlier Smart default of contextual children preserving the parent's calculated output. For **future accepted additions**, Smart Add is a formula-bearing derived-parent transaction. A measured parent may become unavailable until the new inputs are supplied. Its original measurement/source remains reference provenance and in the pre-change checkpoint, not a substitute calculated result. Do not claim that calculated output remains unchanged after this user-authorized transition.

The latest screenshots reportedly show useful, nonempty prepared `gpt-6-luna` suggestions for actual haulage KPIs. This revision is not another empty-result investigation. Preserve the selected model/provider/key, existing bounded preparation and prepared-path speed. No new live model call is required for planning.

They are the working baseline, not files owned by this planning slice. Only this new plan may be written. Do not reset, commit, push, edit earlier plan/log/review, change stored user graphs, migrate existing contextual children, alter their values, restart the user's port-3000 server, or overwrite/delete the user's `.next`. ## Acceptance contract

### 1. Formula-bearing Add and mixed draft

Maintain a frozen `KpiSuggestionSet` as source evidence. Introduce a separate bounded composition draft (for example `KpiIncomingDraftV2`) containing: target/context/proposal identity where applicable, selected proposal keys, manual rows with stable local keys/name/unit, explicitly chosen existing references, final formula, draft revision, and formula authorship (`recipe`, `model`, `user_edited`, or `user`). Original proposal/model provenance remains separate from what the user edits. An edited recipe is not still an exact audited recipe.

Use a single draft per open target/proposal identity. Changing text/names or hovering must not regenerate row keys or launch a provider call. Manual rows and the edited final formula survive background replies, rerenders and commit conflicts; a new prepared proposal is offered by explicit Refresh, never installed over a dirty draft. Manual keys are host-created once (not derived from mutable labels); model/proposed/manual/existing aliases have collision-free namespaces. Show readable reference chips/names; the underlying formula uses stable local aliases. At accepted Add, resolve aliases to actual existing or operation-owned new IDs **once**, by walking the formula AST, never string replacement. Renaming rows preserves their references. Removing/deselecting a referenced row invalidates the formula rather than silently rewriting its business meaning. Alternative switching cannot merge competing decompositions; retain own rows as drafts and require validation against the newly selected alternative.

Concrete recommended shape: `IncomingKpiBatchDraft { groupId?; childKeys; manualChildren:[{key,name,unit,description?}]; existingFactors?:[{key,nodeId}]; formula; formulaAuthorship }`, submitted with `{context, proposal?, draft}`. This is the existing Smart panel/editor with optional preparation, not a new product route or arbitrary graph/sandbox editor.

The initial actionable proposal selects its complete factor group and shows its proposed formula. Add always means **add the final selected/new factors and install that displayed formula**, promoting the parent. There is no default `Add as context` success path and no extra generic approval modal. The editable formula itself is the concrete review surface. Selecting only some original factors or adding own rows makes the composition user-authored: it is allowed once the user supplies a coherent final formula over the exact selected set; it must not secretly keep the old recipe formula or assign equal weights/addition.

Own rows are available while suggestions load, fail, are empty, or are unavailable. Manual-only work needs no configured/invoked model; model-derived rows/formulas retain the current provider/credential lineage and publication revalidation. The panel can therefore perform a genuine partial-proposal + own-row addition, not a choice between an AI mode and a separate manual dialog.

Keep a maximum of **six new proposed/manual rows** in one accepted draft and three proposal alternatives. Separately allow up to **16 distinct explicitly referenced existing KPIs** (direct or shared); an existing reference never consumes a new-node slot. Existing factor coverage must not be dropped to satisfy the new-row cap. Bound the editable local-alias formula to **1,024 characters** and its final ID-expanded formula to **4,096 characters**, in addition to the AST bounds below; existing name/unit/key limits remain. The model wire output stays at six child rows per group, 500 formula characters, three groups and the current byte/token/one-call budgets: the larger local editing allowance is not permission to enlarge model responses or spawn more calls. Host-projected existing references are separate draft inputs, not invented model rows. A graph beyond these local bounds gets an explicit limit error, not partial factor omission. Blank placeholder rows are drafts, not implicit inputs: remove them or leave them unselected. At least one actual change and a nonconstant valid formula are required; a formula-only change using existing factors may be supported explicitly, but an empty/no-op Add must not pass.

### 2. Generic formulas: minimum formal validation

Reuse the existing formula parser/AST/evaluator and ChangeSet pipeline. Extend feature-local Smart validation instead of rewriting the general engine. Admission has two dimensions: deterministic arithmetic/graph safety, and source/authorship/business scope. Passing the first is not certification of causality or data quality.

* Permit only the engine's `+ - * /`, unary minus, parentheses and `min/max` syntax. Bound AST depth (recommend 24), nodes (128) and argument count under the existing row/text caps. Reject unknown symbols/functions, self references, constant-only formulas and malformed/oversized input before candidate construction.
* The exact formula reference set equals the effective selected proposed rows + own rows + explicit existing factors. Unchecked proposal rows are not silently created. Every added factor has a real effective dependency; reject zero-multiplier masking and trivially cancelled/dummy references. Existing target factor children must remain explicitly accounted for; previous context-only children may remain unchanged if unselected. Reuse the full-project visual/formula DAG and effective-reference checks; do not claim to solve general symbolic equivalence.
* Model-authored formulas cannot invent coefficients, averages, weights, observation counts, conversion constants, values or calibration parameters. Retain only reviewed algebraic constants such as `1` in a decimal-fraction complement; measured weights/counts belong in unknown input rows. User-authored finite numeric coefficients are an explicit formula edit, never user-provided measured facts or model defaults; still enforce dimensions, effective references and calculation checks. No automatic coefficient is introduced when selecting a subset.
* Replace the recipe-only arithmetic gate with a small symbolic **unit-expression** algebra over explicit row/target units: additive/min/max operands match, multiplication/division combine exponents, final dimension and scale match the target. Handle haulage quantities such as `km`, `trip`, `km/trip`, `h`, `h/trip`, `km/h`, `t/trip`, count and explicit periods. Accept bounded opaque unit atoms for exact equality/cancellation where safe, with a closed grammar and no eval. Existing exact spelling aliases may remain; unit aliases are not KPI/domain routing.
* Preserve scale/basis: `h` is not silently equal to `min`, `km` not `m`, percent not decimal fraction, currencies not exchangeable, and monthly totals not hourly values. No unrequested scale/period conversion. Initially require same-scale input units or explicit reviewed conversion semantics; a user-entered coefficient alone cannot falsely certify an unsupported conversion. Unknown/ambiguous unit or required period/denominator basis yields a short editable error, not a contextual fallback presented as successful calculation.
* Reuse the resolved analysis-period scope and preserve entity/material/process basis from the actual context. A per-trip ratio can be valid without forcing a fabricated monthly basis. Equal dimensional strings alone do not prove compatible populations, loaded/empty scope or disjoint/exhaustive categories. The model must describe an actual arithmetic definition using measurable inputs from the stated context. Unsupported causality stays a limitation, not a fabricated equation. Do not use `speed=f(gradient)`, arbitrary weighted sums, or partial categories labelled a complete total.

Model output can use the existing wire shape (`selectionMode=all`, all `requiredKeys`, non-null formula, `recipeId=null`) for generic arithmetic if no new fields are required. Tighten the preparation prompt toward computable definitions, retain concise rationale, and validate locally. Do not silently coerce an old contextual `formula=null` result into a sum. It can supply editable starting rows, but Add requires an explicit valid final formula. A genuinely missing definition may return a concise empty/needs-formula result with own-row editing still available; do not force a nonempty invented formula.

Version the changed arithmetic validator and preparation policy/cache keys (next preparation revision after current v2). If the output shape stays unchanged, retain the task/schema ID with explicit semantic-policy invalidation; if fields change, version the wire schema and synchronize every registered transport. Never make arbitrary model-owned unit metadata a bypass to host validation. Historical prepared-latency numbers remain historical evidence; measure the new UI separately.

### 3. Existing factors, shared references and plans

A coherent definition may instead reference the existing distance and a new, independently measured moving-time input with matching scope/units. The time remains unknown; no source total is duplicated or assigned a guessed value.

Support explicit `existingNodeId` factor rows beyond immediate children when required for such definitions: the model may name only an actual bounded-context observed ID, and the user may deliberately choose an existing graph KPI. Add/update `decompositionPlan.sharedWith` for the extra actual formula user where a plan exists. A reused direct child keeps its visual parent and receives the appropriate factor role/relation; a shared reference is a formula dependency, not a newly created child. Show a short `Existing` marker.

Update the target's existing planned `input` entry to `calculated` when it is an active factor, and selected reused context children to input/calculated roles only if they genuinely become root-active through the new formula. It may gain a `calculated` node type and its own validated child formula while retaining `plan.kind=context`, context descendants/edges and no root activation. A direct-root grouping warning remains an incremental construction warning; no full-agent finish bypass is added.
