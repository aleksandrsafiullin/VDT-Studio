## Product outcome and scope

The right action area of a KPI card must reveal the existing Manual, AI and File actions **and** an adjacent Smart suggestions panel on the same hover/focus interaction. The user chooses a coherent decomposition or independent contextual children and adds one immediate layer. Prepared suggestions must appear in under one second without starting the minutes-long tree/deepen agent loop.

Implement all three sources: reviewed executable recipe data when explicitly applicable, persisted per-context suggestions, and bounded preparation through the user's existing backend/model. Prepare selected/visible nodes when opening an existing project, and the next immediate layer after adding nodes. Existing projects without recipe provenance must work through background semantic preparation; they must not be limited to a static demo or require a newly generated tree.

This plan does not promise fresh arbitrary CLI/API/local inference within one second. A genuine cold miss immediately shows `Preparing suggestions…`, and later becomes ready, empty, timed out, unavailable or failed. The three original actions remain usable in those states. A light task never falls back to the full `requestIncomingKpisWithAi`/`deepen_node` run. That existing action remains explicitly available to the user.

No source values, estimates, numeric defaults, evidence, confidence scores or business applicability may be invented. Suggestions are proposals, not certified business models. No new provider/key, change of the selected model, external search, dependency installation or corrective-runtime flag activation is required for this feature.

## Architecture and contracts

### A. Proposal and context contract

Add a small strict browser-safe domain contract and pure compiler/validator, preferably under `packages/vdt-core/src/suggestions/`. Provider prompt/schema/task code belongs in `ai-harness`; canonical recipe extraction stays in `vdt-agent`; scheduling/cache/interaction belongs in web. Keep Node-only skill loading out of browser imports.

A versioned `KpiSuggestionContext` captures workspace/project/VDT/target identity, local semantic revision identity, current durable head/runtime identity where available, original-language business context/goal, industry, period, root, all direct existing children, parent paths, relevant siblings, target name/description/type/unit/formula, data-mapping/value-knownness/provenance category, and root decomposition-plan context. Excerpts are bounded and mark omissions explicitly. Include the target and direct children before optional distant context; traversal must tolerate DAGs and reject/bound cycles. Never reuse `buildDeepenNodeExcerpt`'s unguarded ancestor loop blindly.

Build a memoized semantic graph fingerprint on semantic changes, excluding layout/viewport and unrelated scenario edits. Include all node identities/names/units/formulas/statuses/mapping identities, hierarchy/shared-reference edges, business context, period and decomposition plan so distant shared dependencies cannot leave a stale hit. Compute once per change, not for every mouse movement. Store local `projectRevision` and durable CAS separately for application checks.

Each `KpiSuggestionSet` has strict version, target/context hash, proposal ID, creation/expiry, origin (`recipe` or `model`), exact recipe/version/hash when used, effective backend/model/binding identity for model results, schema/validator/recipe-catalog versions, concise applicability rationale, explicit limitations and up to three alternative `groups`. Each group has stable suggestion-local keys, title, one-level child specs (max six), required factor keys, selection mode, proposed formula over local keys if any, typed dimensional/period contract when verified, and application mode. The server/host generates identities and fingerprints; model output cannot choose actor, durable revision, provider configuration or cache authority.

Alternatives are mutually exclusive. Required multiplication/division/subtraction factors select as one group; no partial formula references. Independently selectable items are contextual influences unless a reviewed recipe explicitly certifies a selected-subset aggregate and makes its partial scope visible. Do not infer that arbitrary selected revenue categories are an exhaustive revenue decomposition. New child values stay absent with `valueStatus=unknown`/appropriate needs-data status; a formula-only literal or hidden assumption cannot manufacture a baseline.

### B. Recipe eligibility and meaning

Use one canonical recipe source and a rebuildable browser-safe projection with recipe/hash/validator identity. Initially audit a small useful set already represented in canonical skills (production volume, time/downtime, quantity-price revenue and revenue components where the canonical source supports them); extend canonical source only if necessary, documenting it. Audit immediate-layer factors, units, period assumptions, existing-child handling and formula completeness. Do not publish `generic_fallback` or incomplete extracted recipes as executable Smart content. A deeper calculated child with no immediate formula must be an explicitly unknown input proposal at this layer, not falsely calculable.

Instant deterministic eligibility requires explicit existing binding/provenance (known selected skill/recipe and role), a previously accepted Smart semantic binding, or exact formal formula/metric identity plus verified preconditions. Names, translation aliases, domain keywords, tags invented from text and retrieval scores cannot select the decomposition. A legacy node with no such binding is cold even if named “Revenue”. Its configured model may explicitly choose a reviewed candidate using a bounded catalog projection and the full relevant context in one light response; persist that decision and rationale with the context. Custom model proposals remain possible when no reviewed recipe applies. The original request language is retained; translated canonical skill copies are forbidden.

### C. Parent calculations, formula replacement and safe application

The panel must distinguish `Add contextual KPIs` from `Add drivers and use formula` using concise product copy and an inline formula preview. There is no extra generic approval dialog.

Default rules:

* A measured/data-mapped parent or a parent with an existing formula keeps its current calculation. Adding suggested contextual children does not silently convert it into a derived KPI or alter its existing formulas, values, sources, mapping or scenario behavior.
* For a blank target, a complete verified group may install its proposed formula. For a measured/formula-bearing target, formula replacement is a separate explicit choice inside the panel with the before/after formula and warning that the parent will now calculate from children. Retain original source metadata/checkpoint; verify the actual calculated root before/after, not just object-field preservation.
* Formula application requires a narrow deterministic unit/period contract for the accepted group. Support only explicitly listed canonical dimensions/conversions in audited recipes (including time basis, currency, count and percentage scale where relevant), validate the AST/reference/dimensional expression and reject unknown conversions. Do not extend the whole formula engine or claim general dimensional certification. A custom model statement of its own validity is insufficient. Unsupported or ambiguous units/time/currency/percent relations are contextual-only, or ask for needed context; never executable by default.
* Existing children, shared dependencies, rejection status, normalized IDs/concepts, formula/visual alignment and cycles must be checked against the **current complete project**. Do not silently duplicate an existing driver, auto-reparent a shared node, suffix a collision and pretend it is a new concept, mix alternatives, overwrite a sibling formula or deepen newly created children. Reuse an existing child only through an explicit verified reference in the group and include it in the formula/selection preview.

Compile selected proposals into one normal `VdtChangeSet`, with fresh host IDs resolved once for all references. Preview, validate graph plus the additional Smart invariants, calculate, and compare errors to the baseline. Unknown newly added inputs and resulting missing-value diagnostics are expected and visible for an explicitly chosen derived formula; new cycles, parse/reference/unit errors or unrelated calculation damage block apply. Do not use the full-model finite-root finish gate to force recursive decomposition or invented values.

Application identity binds proposal/context/selection, active workspace/VDT, local revision/fingerprint and durable expected head/runtime. Recheck at click, before commit and at completion. Double click uses one operation; stale proposals require refresh instead of silently rebasing.

For a stored VDT, build the candidate including a pre-change version checkpoint and submit it through `saveStoredVdtRevision` with an operation-owned `smart-apply:<vdtId>:<uuid>` key, exact `revisionCasFromHead`/runtime CAS, and user-source summary. Keep request bytes/IDs/CAS/key immutable across ambiguous network retry. Do not call `saveActiveWorkspaceVdt` later on a possibly different project and call that atomic. Show `Adding…`; replace the local project only after successful commit and unchanged local identity. A short mutation-in-progress guard prevents new graph edits/agent starts in the UI while the commit settles; the store must still reject stale completion if an agent snapshot, navigation or external edit races it. On commit conflict preserve the user's local project and selection, refresh authority, and surface reload/review. Do not mark saved, clear the operation as succeeded, change to a newer head and retry, or overwrite the user's local draft. A commit acknowledged after the local identity changed updates only its owning VDT metadata and exposes reconciliation, never replaces the new/current project. An active mutating agent run blocks Smart **apply** until it finishes/cancels; suggestions themselves remain read-only and inspectable.

For a scratch project with no stored VDT, the same validated transaction creates one local draft mutation/checkpoint with guarded Undo and normal draft persistence, explicitly unsaved. Later normal workspace creation uses the existing combined initial-snapshot path. Never label scratch/local-storage acceptance a durable SQLite commit; hosted write policy remains unchanged.

Undo is a named guarded Smart operation. It requires the same VDT, the exact post-apply local content identity and (for a stored VDT) the post-apply durable head. It restores the checkpoint through a **new** normal CAS revision with its own immutable `smart-undo` operation key; it does not rewind/delete durable history. A changed head/local graph disables direct Undo and directs the user to Versions. An ambiguous retry replays the same operation. Retain before/after identities across reload if showing a reload-persistent Undo; otherwise clearly scope the button to the current session and keep the checkpoint in Versions. Do not reuse `versionRestoreUndo` without preserving its existing behavior.

### D. Lightweight preparation through the chosen execution mode

Introduce canonical read-only task `suggest_incoming_kpis` / schema ID `suggest-incoming-kpis-v1`. Register its limits, browser exports, local JSON schema/fixtures and manifest task/schema allowlists. It makes **one** structured completion and deterministic validation; no agent bootstrap/classifier, research, tool loop, repair loop, full-tree generation or graph write. No reuse/resume of the user's active CLI agent session for speculative hover work.

Reuse `resolveExecutionSettings`, effective model selection, encrypted credential handling, app-mode checks and the existing execution client/provider security boundaries. Add an explicit suggestion client/service branch where current adapters are incomplete:

* API/BYOK uses the selected protocol/model/key and existing allowlisted endpoint/SSRF/redirect policy.
* Managed subscription CLI uses the selected manifest-owned backend/model through its bounded read-only completion service and owned isolated work directory; paired standalone runner/desktop uses the registered task/schema transport. Do not silently substitute another CLI or turn the full agent profile into a different execution profile. Where the existing selected adapter cannot safely expose this capability, return typed `suggestions_unavailable` for that adapter and document it, rather than falling back or weakening isolation. Supporting the configured trusted-local Codex path used by this app is an implementation acceptance target; it must not be left as an always-unavailable stub.
* Local models use the selected trusted-host registered model binding and manifest-owned endpoint. Add read-only task support at that boundary rather than feeding the full local agent tool prompt into a tiny task or accepting a client-supplied localhost endpoint. Supporting available local HTTP bindings is an implementation target, not an optional future item.

Use a compact bounded excerpt and reviewed recipe cards, no source files/raw rows, full project versions/chat, secrets in prompts/cache/logs, or server/env fallback that changes effective selection. Bound UTF-8 input to 24 KiB, output to 16 KiB and max three groups/six children each. API/local providers must enforce a 2,048 response-token limit unless schema-size evidence requires a reviewed increase. The inspected installed Codex CLI exposes no supported hard output-token flag: request 2,048 in its prompt, enforce hard one-invocation/wall-time/stream-output limits, and explicitly leave its private token ceiling unqualified; never invent a configuration key or claim a prompt is a hard cap. Deadline: API/local 15 s and CLI 30 s, additionally capped by the user's configured lower timeout. Abort propagates through HTTP/provider/runner cancellation and child termination before owned temporary cleanup. A timeout yields an honest state, not an empty successful proposal. Model output cannot expand a budget, choose executable commands or mutate selection/provider state. Tests use fake providers and transport fixtures; live selected-backend evidence is a separate claim.

### E. Persistent cache and bounded one-layer scheduler

Use a separate rebuildable origin-local cache (IndexedDB with guarded in-memory fallback), not a new SQLite authority or mutable field in `VdtProject`. Persist **validated** proposal artifacts/provenance only; never keys, pairing tokens, processes, AbortControllers, pending jobs or private raw prompts. The cache key binds workspace/project/VDT/target, semantic context hash, recipe-catalog/schema/validator version, and effective nonsecret backend/model/binding identity for model results. A credential/settings epoch can invalidate without hashing/persisting a secret. Scope all results and negative states; validate cache contents/TTL/schema at hydration and apply. Cached model proposals remain untrusted data until local revalidation.

Initial caps: 256 entries and 2 MiB across the origin, seven-day TTL for accepted validated proposal artifacts, 30-second empty/failure cooldown, LRU eviction only inside this feature's cache. Storage failure disables persistence but not local suggestions or editing. Changing relevant context/provider/recipe version invalidates the old apply identity. Visible suggestions remain frozen while the user is selecting; a changed context marks them stale and disables add, and a refresh is explicit. A background result cannot replace a checked list under the cursor.

Maintain one scheduler per active workspace, one provider request in flight, queue at most 12, deduplicate by full key, prioritize active/hovered/focused node then selected then newly added then viewport-visible nodes. On open/hydrate start local/cache preparation, and at idle prepare the selected node plus at most six visible unprepared nodes through the selected backend. After apply/generation/import/manual addition, queue the immediate children (at most six) for one-level-ahead preparation. Never recursively walk descendants or launch provider work for every mounted/offscreen card. Numeric values and movement alone do not refill the queue. Cancel/reject old results on project switch, node deletion, semantic/binding change and component disposal; do not cancel an otherwise useful deduplicated job merely because the pointer briefly leaves.

Bound speculative work to eight provider requests per workspace activation/context generation, with one attempt per key and cooldown; changing viewport or repeated hovers cannot reset that budget. Explicit `Prepare/Retry` for the active node can request one new bounded attempt, exposing depleted budget/unavailable state. Persisted successful cache avoids repeated cost after reopening. Background preparation must yield while a full user agent run is active or the page is hidden. Record budget/cancellation counters for tests and diagnostics without sensitive content. These caps are initial reviewed constants, not a claim that every node of an arbitrary large tree is prewarmed.

## UX and accessibility

Use one anchored popover/panel beside the active right rail, with enough pointer-hit-area bridge between rail and panel, viewport collision handling, max height/scroll and React Flow overlay/z-index placement. Show the first local/cache result immediately and a short preparation/empty/error status otherwise. Limit delay on hover activation to 100 ms; a 150–250 ms close grace can prevent accidental collapse. Keep it open while pointer or focus is inside either surface; Escape closes and restores focus, outside click closes, and Tab can reach the three actions, alternatives, checkboxes and add button. Provide an explicit focus/touch-accessible Smart trigger while right-side hover opens the panel automatically.

Use actual radio/checkbox semantics and associated labels for alternatives/groups, concise child names/units and an inline formula preview/application choice. No required factor may be deselected independently. Show provenance simply (`Library`/`Prepared`) and limitations without claiming an AI result is verified. No disabled list that permanently says “coming soon”. Preserve selection while staying on one proposal; changing alternatives clears incompatible picks. Disable add for zero selection, stale context, invalid group, active mutation or commit-in-progress, with a short actionable reason.

All interactive surfaces use `nodrag nopan nowheel` and stop the appropriate pointer/mouse/key propagation without suppressing native checkbox/button accessibility. Clicking/tapping/scrolling the panel must not select/move a KPI, pan/zoom the canvas or start an edge connection. The panel must work at viewport edges and common graph zoom levels without being clipped by another node. Original manual/AI/file actions, keyboard selection and graph connections must retain their behavior.
